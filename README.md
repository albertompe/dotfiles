# dotfiles

My personal dotfiles and environment configuration, managed with
[chezmoi](https://www.chezmoi.io/).

The configuration is templated and OS-aware, so the same repository can be
applied to a Linux workstation, a headless Linux box or VM, a Red Hat based
server, or a macOS laptop while keeping machine-specific data (secrets,
per-account settings) out of version control.

## What you get

- Shell setup: Zsh with zinit, tmux (+ cheat sheet), and a theme-switchable
  prompt (Oh My Posh / Oh My Zsh + Powerlevel10k / Starship). See
  [Shell setup](#shell-setup).
- Core utilities via [mise](https://mise.jdx.dev/): a version-managed toolset
  (Go, Python, Rust, Kubernetes, Terraform, Git tooling, etc.) declared in
  `dot_config/mise/config.toml`.
- Editors: Neovim, plus WezTerm, Zed and VS Code setups.
- Git: a base `~/.gitconfig` generated by template (identity, signing, aliases,
  workflow settings); per-account identities activated by directory
  (`~/.gitconfig-inditex`, `~/.gitconfig-albmtez`).
- Container/virtualization support (Podman/Docker/KVM) and misc system
  packages, installed only when applicable.

## Shell setup

The default shell is **Zsh**, configured through `~/.zshenv` and modular files
under `~/.config/zsh/` (loaded in order: `10-main`, `15-aliases`,
`20-keybindings`, `25-common-system`, `30-common-dev`, `35-cleanup`,
`40-containers`, plus `linux-specific/` or `macos-specific/` per platform).

### Plugin manager — zinit

Plugins are loaded with [zinit](https://github.com/zdharma-continuum/zinit)
(installed on first launch, stored under `~/.local/share/zinit`):

- `zsh-users/zsh-completions`, `zsh-autosuggestions`, `zsh-syntax-highlighting`
- `Aloxaf/fzf-tab` — fzf-based completion menu with previews (e.g. directories
  for `cd`), group switching with `<`/`>`, and an fzf popup inside tmux
- `junegunn/fzf` — fuzzy key bindings and completions (`CTRL-T` files,
  `CTRL-R` history, `ALT-C` directories), loaded with `wait` + `lucid` ice
- `ohmyzsh/ohmyzsh` and `romkatv/powerlevel10k` — only when the `omz` prompt is
  selected

`zinit-update` re-runs `zinit self-update` + `zinit update --all`.

### Prompt and themes

The prompt and theme are global, selected once in `dot_zshenv` (`~/.zshenv`):

- `SELECTED_PROMPT` — `omp` (default, Oh My Posh), `omz` (Oh My Zsh +
  Powerlevel10k), or `starship`.
- `DOTFILES_THEME` — `nord` (default) or `onedark`. It drives the prompt color
  palettes and is propagated to `WEZTERM_THEME` and `STARSHIP_THEME`.

Prompt engines:

| Selector    | Engine             | Config / theme                                                        |
| ----------- | ------------------ | --------------------------------------------------------------------- |
| `omp`       | Oh My Posh         | `~/.config/zsh/oh-my-posh/omp-config.toml` (palette-driven)           |
| `omz`       | Powerlevel10k      | `powerlevel10k` via zinit + themes in `~/.config/zsh/p10k-themes/` (`p10k-lean.zsh`, `p10k-pure.zsh`) |
| `starship`  | Starship           | `~/.config/zsh/starship/starship.toml` (nord/onedark palettes)        |

With the `omz` prompt, Powerlevel10k's instant prompt is enabled when the
cached theme file exists, and editing it works through `p10k configure`.

### History and key bindings

- History is stored in `~/.zsh_history` (size 10000) with `append_history`,
  `share_history` (shared across tabs) and `hist_ignore_all_dups`.
- Up/down arrows perform **fuzzy history search** (`up/down-line-or-beginning-search`),
  with bindings for both `\e[A/C` and `\eOA/C` so they work on Linux and macOS.
- Home/End move to the beginning/end of the line.

### Completion

- `compinit` with caching, menu (`select=long-list`), grouping, and max-error
  tolerance.
- fzf-tab replaces the default menu; `git checkout`, `cd` (eza preview), and
  colorized entries are tuned via `zstyle`.
- Tool completions are wired for `oc`, `kubectl`, `docker`, `podman`, `k3d` and
  `terraform`.

### Aliases and helpers

- Editors: `vim`/`vi`/`v` → `nvim`.
- Listing: `ls`/`l`/`la`/`ll` plus `eza` variants with icons (`ezal`, `ezas`,
  `ezam`, `ezae`, `ezag`, `ezad`, `ezar`, `ezatree`).
- Kubernetes: `k` (`kubectl`), `kcc`/`kns` (kubectx/kubens), `kg*` getters for
  pods, deployments, services, secrets, etc.
- `batdiff` shows `git diff` through `bat`.
- Update helpers: `zinit-update`, `chezmoi-update`, `mise-update`,
  `krew-plugins-update`.
- Disk/housekeeping helpers (in `35-cleanup.zsh`): `clean-snap`,
  `clean-docker` (`--all` for deep clean), `clean-apt`,
  `clean-journal-logs`, `clean-mise`, `clean-go`, `clean-python`.

### Environment and PATH

- `~/.local/bin`, `~/scripts`, `~/.lmstudio/bin`, krew bin dir, Rancher Desktop
  (`~/.rd/bin`) and `~/.antigravity` are added to `PATH` when present.
- `mise activate`, `zoxide init`, `direnv hook` and Oh My Posh / Starship init
  run at startup.
- The optional `~/dev-tools/dev-profile` file is sourced for extra dev
  environment setup.

## Supported platforms

| Platform              | Package managers                                    |
| --------------------- | --------------------------------------------------- |
| Linux Debian/Ubuntu   | APT + Flatpak (+ Snap when available) + mise        |
| Linux Red Hat family  | DNF (Fedora/RHEL-based) + Flatpak + mise            |
| macOS                 | Homebrew (formulae + casks) + mise                  |

GUI applications are installed primarily through **Flatpak** (Flathub, user
scope) on Linux; **Snap** is also supported as a fallback when the Snap daemon
is present. macOS GUI apps come from Homebrew casks. kubectl plugins are
installed through **krew**, and a complete CLI toolchain through **mise**.

## How it works

Chezmoi stores your dotfiles in a source state: every file prefixed with `dot_`
maps to a hidden file in your home directory (e.g. `dot_zshrc` → `~/.zshrc`).
Templates (files ending in `.tmpl`) are rendered at apply time, driven by data
declared in `.chezmoi.toml.tmpl` (which generates `~/.config/chezmoi/chezmoi.toml`).

Machine-specific data stays out of the repository:

- Secrets for templates (git identity, signing keys, main SSH key) live in
  `~/.private.zsh` and are read directly by the templates.
- Per-account git configs (`~/.gitconfig-inditex`, `~/.gitconfig-albmtez`)
  are created locally, not versioned, and activated with `includeIf` from
  `~/.gitconfig.local`.

See [Git configuration](#git-configuration) for details.

## Git configuration

The base `~/.gitconfig` is generated by the template `dot_gitconfig.tmpl`. It
ships static, machine-independent settings (workflow options such as
`pull.rebase` + `autostash`, `push.autoSetupRemote`, `fetch.prune`, `rerere`,
`merge`/`diff` styles; the `st`, `co`, `br`, `lg`, `unstage`, `last`, `amend`
aliases; and a final `[include]` of `~/.gitconfig.local`).

Your personal values are kept out of the repository: the template reads them
directly from **`~/.private.zsh`** (a private, non-versioned file in your home).
Use `dot_private.zsh.example` in this repository as a reference.

| Variable                 | Purpose                                              |
| ------------------------ | ---------------------------------------------------- |
| `GIT_USER_NAME`          | Full name used in commits                            |
| `GIT_USER_EMAIL`         | Commit email                                         |
| `GIT_GITHUB_USER`        | GitHub username (`[github] user`)                    |
| `GIT_SSH_KEY`            | Default SSH key for GitHub (`core.sshCommand`)       |
| `GIT_SIGNING_KEY`        | GPG signing key — optional, enables `gpgSign`        |
| `GIT_SSH_SIGNING_KEY`    | SSH signing key (e.g. `~/.ssh/key.pub`) — optional; takes precedence over GPG when both are set |

If `~/.private.zsh` is missing (e.g. first apply on a new machine) the values
render empty and git keeps working; create the file and re-run
`chezmoi apply`. With a signing key, commits are signed (GPG via
`[user] signingkey` + `[commit] gpgSign`; SSH via `[gpg] format = ssh`).

### Extending the git config

`~/.gitconfig` ends with `[include] path = ~/.gitconfig.local`, so everything
machine-specific lives there — never in the versioned template. Typical use:

- Remote/URL rewrites or extra global settings for this machine.
- Activation of per-account identities through `includeIf`:

  ```ini
  [includeIf "gitdir:~/code/inditex/"]
      path = ~/.gitconfig-inditex
  [includeIf "gitdir:~/code/albmtez/"]
      path = ~/.gitconfig-albmtez
  ```

The included per-account files (`~/.gitconfig-inditex`, `~/.gitconfig-albmtez`)
hold that account's identity, SSH key and, if applicable, corporate tooling
(credential helper, trace2); they are deliberately machine-local and not
versioned. Git silently ignores missing include targets, so machines without
those account directories work out of the box.

## Requirements

- Git, curl, zsh (installed by the setup when missing).
- A GitHub token with permission to read public repositories for the tool
  downloads; see [below](#github-token).
- An interactive terminal for the prompts during `chezmoi init`. For automated
  installs set the environment variables described in
  [Installation options](#installation-options).

## Installation

```sh
GITHUB_TOKEN=ghp_YOURTOKENHERE sh -c "$(curl -fsLS get.chezmoi.io)" -- -b ~/.local/bin init --apply albertompe
```

This one-liner:

1. Installs the `chezmoi` binary into `~/.local/bin`.
2. Clones the dotfiles source repository.
3. Generates the local `~/.config/chezmoi/chezmoi.toml` (answering the
   [interactive prompts](#interactive-prompts)).
4. Applies the target state: writes all dotfiles, schedules and runs the one-time
   provisioning scripts (system packages, Flatpaks, mise tools, krew plugins…).

> Install as your regular user. Some provisioning steps use `sudo` and will ask
> for your password.

Do not run this command from inside an existing home-directory checkout; chezmoi
will initialize and manage the source directory itself.

### `--apply`: is it necessary?

Yes, include `--apply` for a one-shot install. Without it `chezmoi init` only
clones the source and generates the configuration; nothing is applied, so you
would have to run `chezmoi apply` afterwards to actually install your dotfiles
and run the provisioning scripts.

Alternatively, run the two steps separately:

```sh
sh -c "$(curl -fsLS get.chezmoi.io)" -- -b ~/.local/bin init albertompe
chezmoi apply
```

If your repository is private, initialize over SSH (keys already configured) or
provide the token for HTTPS:

```sh
GITHUB_TOKEN=ghp_YOURTOKENHERE sh -c "$(curl -fsLS get.chezmoi.io)" -- -b ~/.local/bin init --ssh --apply albertompe
```

### `GITHUB_TOKEN`

The token is necessary for the **mise** provisioning stage: mise installs the
CLI tools declared in `~/.config/mise/config.toml` by downloading them from
GitHub releases. Unauthenticated requests are subject to GitHub's download rate
limits (~60 requests/hour/IP), which will frequently abort the installation of
a multi-tool toolset. A personal access token raises those limits and makes the
install reliable.

The value is exported in the environment of the provisioning script for the
duration of the install and is never persisted or written to any file.

## Installation options

All options can be set as environment variables before `chezmoi init` to skip
the interactive prompts (also useful for CI/scripted installs). Accepts
`true`/`1`/`false`/`0`.

| Variable                          | Default | Effect                                                               |
| --------------------------------- | ------- | -------------------------------------------------------------------- |
| `CHEZMOI_HEADLESS`                | prompt  | Headless machine (no GUI): skips GUI packages, Flatpaks, GUI tools. In containers it is forced to `true`. |
| `CHEZMOI_MISE_TOOLS`              | `true`  | Install the default mise tools from `~/.config/mise/config.toml`. Set to `false` for a `bare` mise where only the tools declared in each project's `mise.toml` are installed on demand. |
| `CHEZMOI_ENABLE_CONTAINER_SERVICES` | prompt | Enable container services (Docker daemon, Podman socket) — useful on LXC/systemd hosts. |
| `CHEZMOI_ENABLE_KVM`              | `true`  | Set up the KVM/libvirt hypervisor and VM tooling (skipped inside containers). |

Example non-interactive headless install with default tools:

```sh
CHEZMOI_HEADLESS=true CHEZMOI_ENABLE_CONTAINER_SERVICES=false CHEZMOI_ENABLE_KVM=false \
GITHUB_TOKEN=ghp_YOURTOKENHERE sh -c "$(curl -fsLS get.chezmoi.io)" -- -b ~/.local/bin init --apply albertompe
```

Example bare-mise install (only project-scoped tools):

```sh
CHEZMOI_MISE_TOOLS=false GITHUB_TOKEN=ghp_YOURTOKENHERE \
sh -c "$(curl -fsLS get.chezmoi.io)" -- -b ~/.local/bin init --apply albertompe
```

Containers are detected automatically through `/.dockerenv` (or the chezmoi
`isolation` value) and default to `isHeadless=true`, `enableKvm=false`.

## Interactive prompts

During `chezmoi init` (when the corresponding variable is not set) you are
asked:

1. Is this a headless machine (no graphical user interface)? *(default: no)*
2. Install the default mise tools (from `config.toml`)? *(default: yes)* —
   answering no gives a bare mise driven only by per-project `mise.toml` files.
3. Do you want to enable container services (Docker daemon, Podman socket)?
4. Do you want to set up KVM/libvirt (hypervisor and VMs)? *(default: yes)*

Answers are stored in `~/.config/chezmoi/chezmoi.toml` and drive template
rendering and the provisioning scripts.

## What gets installed

Execution order (`run_once_*` scripts, in the order the names are sorted):

1. `00` — System packages on Linux: common CLI/GUI, plus Debian/Ubuntu (apt) or
   Red Hat family (dnf) specific sets, from `.chezmoidata/packages.toml`.
2. `01` — Homebrew on macOS (installs Homebrew if missing).
3. `02` — Homebrew formulae and casks on macOS, from `packages.toml`.
4. `10` — Flatpak GUI/CLI apps from Flathub (Linux, user scope, skipped when
   headless).
5. `11` — Snap applications (skipped cleanly when the Snap daemon is absent).
6. `15`–`18` — Zed, WezTerm, VS Code and Chrome (skipped when headless).
7. `20` — mise CLI (installs/updates it).
8. `after 10` — mise tools declared in `config.toml` (uses `GITHUB_TOKEN`).
9. `after 20` — krew kubectl plugins, from `.chezmoidata/krew.toml`.
10. `30`–`32` — Podman/Docker and KVM/libvirt setup (skipped when not enabled
    or inside a container).

GUI applications come primarily from **Flatpak**; **Snap** covers the cases
where Flatpak is not an option; on macOS the GUI apps are Homebrew **casks**.
All CLI tooling is provided through **mise**, APT/DNF/Homebrew packages, and a
set of **krew** plugins for `kubectl`.

## Managing changes after install

Work on the local clone of the repository and re-apply often:

| Target             | Description                                                      |
| ------------------ | ---------------------------------------------------------------- |
| `make help`        | Show all available targets                                       |
| `make diff`        | Dry-run preview of pending changes                               |
| `make apply`       | Apply changes (dotfiles + templates) without forcing scripts     |
| `make init`        | Re-run the interactive chezmoi configuration                     |
| `make force-scripts` | Re-run all one-time provisioning scripts                        |
| `make test-headless` | Simulate a headless install (dry run)                          |
| `make clean-state` | Purge local chezmoi state buckets                                |
| `make audit-brew`  | Compare installed Homebrew packages against the manifest         |
| `make audit-flatpaks` | Compare installed Flatpaks against the manifest               |
| `make audit-zed-extensions` | Compare installed Zed extensions against the settings  |

New tools installed with `mise use -g` write to `~/.config/mise/config.toml`;
copy that entry into `dot_config/mise/config.toml` to track it here. Mise
settings live separately in `dot_config/mise/config.local.toml` so they apply
even when the default toolset is disabled.
